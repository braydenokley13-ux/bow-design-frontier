# 01 DC semantics: what Decision Challenges' code actually does

Scope: DC = `dc-os` @ e1d05104 (Codex frontier). Paths are `DC:src/...` unless noted. "Code" means cited source; "doc" means a claim I did not confirm in code. Labels: EARNED / RECURRING (within DC only) / HYPOTHESIS / REJECTED.

**Headline.** DC's shared semantics are read-side and replay-side, layered over per-family frozen reducers. There is no common act/object address, shared responsibility type or universal compiler, and DC refuses all three in writing. The parent brief's implication of an address scheme in `kernel/refs.ts` is wrong (c3).

## Platform-like but assessment-specific (do not promote)
Rubric levels 0/2/3/4/5 and support caps (`support.ts:22`, `competency/types.ts:142`); Evidence Requirement observers, EvidencePlan and denominators; evidence modes; evidence lane school/synthetic/historical-unknown (`server/evidenceLane.ts:13`, a frozen-permission claim); teacher score or override writes; the forbidden-words recognition guard (`history.ts`, child-safety policy); the closed "product facts" analytics spine (`platform/facts/types.ts:5`, "not evidence").

## (a) Five most likely platform-level
1. Verified transition (#1): replay from a pinned start, refuse on divergence or mutation.
2. Information at the act (#4): available vs opened-with-ref vs knowable-per-input, comprehension explicitly unknown.
3. Exact cuts with typed absence and unknown (#3, #5): present/absent/unmodeled at a named act.
4. Version discipline (#10): exact tuples, `null` never means current, withheld not rewritten.
5. Modeled branch that is never a second history (#6).

## (b) Three most likely vertical-specific
1. The assessment chain and support-cap arithmetic (rubric, denominators, lane).
2. The finance-object grammar: receipt vs plan vs promise vs fee, held vs scheduled wages (Credit terms `creditTermsV1.ts`, "deliberately Credit-v1-specific").
3. Rule-input ledgers (`decisionRuleInputsV1.ts`): demand row, spoilage and fee terms are Market/Credit content.

## (c) Contradictions and tensions
1. `provenance/types.ts:13` and `attemptProvenance.ts:124` hard-code source `exposure:"not-recorded"`, but `attemptChronology.ts:339-346` records open and request events for authored forms. The graph under-reports openings and has no "opened" edge.
2. RESPONSIBILITY_CONTRACTS.md gives a 10-question "exact contract"; code has ≥3 key sets and validates almost none of it (#12).
3. The parent brief lists `refs.ts` as an address scheme; it holds Artifact/Context/Subject/Provenance refs only, and the kernel has no runtime consumer (#9).
4. MOMENTS_AND_RECOGNITION.md:19 and BOW_HOME.md:7 say replay "depends on active package constants" and that Shift uses latest-run storage. Code uses explicit frozen tuples (`syntheticArchive.ts:162-176`) and Shift has archives (`shiftArchiveV1.ts`, `shift/archiveV2.ts`). A decoder *registry* is indeed absent (two hard-coded decoders).
5. "Stable" event identity (ADR:27) vs position-not-identity (`runCopies.ts:92`): ids are stable only inside one replay-verified attempt.
6. DC-main's `WorldObjectIdentity{id,kind,label}` (`domain/world/objects.ts:11`) is a second, older object identity scheme beside #2.

## DC-61 divergence check
No semantic fork. `decisionRuleInputsV1`, `marketEpisodeV1`, `creditObjectReading`, `creditEpisodeV1`, `decisionTrace`, `syntheticArchive`, `objectContinuity`, `kernel/refs` and `provenance/types` are byte-identical to DC, so PR-61's three requests (opened sources with sourceId+eventRef; per-input `knowableBeforeAct`; coded Credit unknowns) exist identically in both. PR-61 only consumes them ("never from a local scan", `marketEvidenceWorld.ts`) and adds a presentation `WorldCut` before/after. It lacks Kit Return and Cycle 59's `readDecisionTimeInformationFromReceiptV1`; DC lacks PR-61's `experience/MarketEvidenceWorld` and `experience/shift`. DC-main has no kernel, provenance or consequential code; it supplies only the refusal "not as a universal ECS" (`docs/NEXT_AVERY_ARCHITECTURE.md:220`).
